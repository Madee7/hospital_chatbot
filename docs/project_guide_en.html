1. Overview and Project Status

This project is an integrated backend for a hospital chatbot operating through the WhatsApp Cloud API. Patients can select a language, specialty or physician, view physician cards, choose a date and time, confirm a booking, and reschedule or cancel an appointment. All core operations are stored in PostgreSQL and displayed in a Streamlit administration dashboard.

Current supported execution path: run uvicorn app.main:app. Root-level files such as main.py and main_ai.py are older experiments and are not the current production entry point.

Patient Interface

  • WhatsApp text, buttons, lists, image cards, and an optional WhatsApp Flow.
  • Arabic and English support.
  • Booking, rescheduling, cancellation, inquiries, and receptionist handover.
  • Voice messages with speech-to-text conversion.

Administration Interface

  • Streamlit dashboard.
  • Clinic, department, physician, working-hours, and holiday management.
  • Appointments, change history, conversations, and reminders.
  • KPIs, usage, and estimated cost.

5. Startup and Entry Points

Supported API

app/main.py creates the FastAPI application, runs create_tables() on startup, and includes webhook_router and booking_router.

  • GET /: confirms that the server is running.
  • GET /webhook: Meta verification handshake.
  • POST /webhook: receives messages and delivery statuses.
  • GET /booking/departments: specialty list.
  • GET /booking/doctors: physician list.
  • GET /booking/doctors/{id}/slots: available times.
  • POST /booking/confirm: direct confirmation for tests without WhatsApp.
  • GET /docs: FastAPI Swagger UI.
Database: app/db/database.py builds an engine with connection pooling and provides SessionLocal and the get_db dependency. Creating tables with Base.metadata.create_all is suitable for development; Alembic migrations are preferable in production.

6. WhatsApp Message Journey Across Files

  1. The patient sends a message to the WhatsApp Business number.
  2. Meta sends JSON to POST /webhook in app/api/routes/webhook.py.
  3. receive_webhook identifies text, button, list, Flow, audio, or a status update.
  4. Text/button input is sent as a background task to _handle_message.
  5. _handle_message opens a database session and calls process_incoming_message.
  6. conversation_engine.get_graph() runs LangGraph.
  7. node_persist_inbound stores the Conversation and Message.
  8. node_handle reads conversation state and performs the appropriate step.
  9. Services read/write PostgreSQL, then whatsapp_client.py sends the Meta response.

7.1 Selecting a Specialty and Physician

  • intent_service.detect_intent recognizes booking intent using rules first.
  • doctor_service.list_departments retrieves departments; the department is the specialty shown to the patient.
  • doctor_service.list_doctors_by_department retrieves physicians in the specialty.
  • doctor_card_payload prepares the name, image, specialty, and biography.
  • whatsapp_client.send_doctor_cards sends cards sequentially (up to five).
  • If WhatsApp Flow is enabled, flow_service builds a carousel and radio list; it falls back to cards on failure.

7.2 Generating and Displaying Times

  • booking_service.get_available_dates_and_slots validates the physician and releases expired holds.
  • slot_service.ensure_slots_for_doctor generates slots from the physician's weekly hours.
  • It excludes past times, minimum booking lead time, physician leave, and clinic holidays.
  • list_available_slots returns only available slots for the same physician and clinic.
  • group_slots_by_date groups them by date for WhatsApp lists.

7.3 Temporary Hold and Confirmation

  1. hold_slot locks the slot row with SELECT FOR UPDATE.
  2. It changes status from available to held, for three minutes by default.
  3. It associates the hold with the WhatsApp number using a marker in updated_by.
  4. The patient enters a name, and MRN/DOB if required by configuration.
  5. The bot presents a summary and waits for “Confirm” or “Cancel.”
  6. confirm_booking locks the row again and verifies that the time is available to that number.
  7. It creates or updates Patient and creates an Appointment with confirmed status.
  8. It changes Slot to booked and clears hold expiry.
  9. It creates AppointmentHistory and Reminder records and closes the Conversation.
  10. It commits and returns a reference such as APT-....

Preventing Double Booking

Protection is layered: the slot row is locked transactionally; booked slots are excluded from available times; and a partial unique index named uq_appointment_active_slot prevents more than one active Appointment for the same slot. With two simultaneous attempts, the second sees the booked status and fails.

8. Rescheduling and Cancellation

Rescheduling

  1. list_upcoming_appointments_for_phone lists only confirmed appointments belonging to the patient's number.
  2. The patient selects an appointment, then a new physician/date/time.
  3. The new time is held for the same WhatsApp number.
  4. reschedule_appointment verifies ownership and the cutoff.
  5. The old slot becomes available and the new slot becomes booked.
  6. The Appointment is updated and an AppointmentHistory record is added.
  7. Old reminders are cancelled and reminders are created for the new time.

Cancellation

  1. The patient selects an appointment and confirms cancellation.
  2. cancel_appointment verifies the phone number, appointment, and confirmed status.
  3. The Appointment becomes cancelled.
  4. The Slot becomes available, making it visible to another patient.
  5. AppointmentHistory is written and pending reminders are cancelled.
Cancellation and rescheduling are subject to CANCEL_CUTOFF_HOURS and RESCHEDULE_CUTOFF_HOURS. If the appointment is closer than permitted, the request is transferred to reception.

9. Working Hours, Slots, and Holidays

Weekly Working Hours

DoctorWorkingHours defines weekday (0=Monday…6=Sunday), start and end time, appointment length, and maximum capacity. The dashboard saves hours through admin_dashboard_service.upsert_working_hours, then automatically generates slots.

Physician Leave

DoctorUnavailability closes a specific physician between two dates/times. When added through the dashboard, overlapping available times become blocked.

Clinic Holiday

ClinicHoliday closes the entire clinic. block_available_slots_for_range blocks available slots for every physician in the range.

10. Reminders

  • create_booking_reminders creates pending records before an appointment (24 and 2 hours by default).
  • process_due_reminders retrieves due records and sends a localized WhatsApp message.
  • Dry-run shows what would be sent without actually sending it.
  • cancel_pending_reminders cancels pending records when an appointment is cancelled or rescheduled.
  • Webhook statuses update a reminder to delivered/read/failed according to Meta receipts.
  • The dashboard displays records and supports dry-run processing and retrying failures.

Manual execution uses app/scripts/run_reminders.py; the command can be scheduled through Task Scheduler or cron.

11. Voice Messages

  1. The webhook detects message.type = audio and extracts media_id.
  2. voice_service.transcribe_whatsapp_audio calls voice_processor.process_whatsapp_audio.
  3. It downloads audio from Meta, sends it to Groq Whisper, and deletes the temporary file.
  4. A voice-type Message and VoiceMessage metadata are stored in the database.
  5. If confidence is low, the bot asks the user to record again or type.
  6. If confidence is adequate, it displays the transcript and asks “Is this correct?” before continuing the flow.
test.py contains an older EgypTalk local ASR prototype, while the active path in app/services/voice_service.py imports voice_processor.py, which uses Groq Whisper.

12. Safety and Reception Handover

  • core/safety.py recognizes high-risk medical phrases and does not provide a diagnosis.
  • It sends a language-appropriate emergency message and creates an urgent HandoverCase.
  • handover_service.create_handover links the case to the conversation and patient, if available.
  • It stores the handover reason, priority, open status, and a summary of recent messages.
  • If a reception number is configured, reception can be notified through WhatsApp.
  • Unexpected webhook errors also become high-priority handovers.

18. Current Technical Notes and Limitations

  1. Legacy path: do not run uvicorn main:app for the current system; use app.main:app.
  2. Draft memory: not all temporary booking details are database-backed; a restart during the flow may return the user to the menu.
  3. Hold ownership: currently stored as a marker in updated_by, not a dedicated column; a held_by_phone column would be clearer in the future.
  4. Timezone: many comparisons use naive datetimes and utcnow(), despite the Clinic timezone.
  5. 30 minutes: the demo assumes 30 minutes, but the dashboard permits changing slot length; keep it at 30 for the demo to work as intended.
  6. Reminder delivery: current sending uses session messages/buttons; Meta templates are more appropriate outside the 24-hour service window.
  7. Alembic: the library is installed but no migrations directory is visible; production needs migrations instead of relying only on create_all.
  8. Authentication: the dashboard uses a simple environment-password comparison, not a complete hashed-password/session system.
  9. Tests: there is no organized test suite for the current path; test.py is an audio prototype, not an automated test.
  10. Legacy cleanup: moving old files to an archive directory would reduce the risk of launching the wrong application.

Summary

The current design cleanly separates HTTP, the conversation engine, business logic, and the database. The key path is webhook.py → conversation_engine.py → services → models/PostgreSQL → whatsapp_client.py. The Streamlit dashboard uses the same database, so bookings, rescheduling, and cancellations appear immediately in administration screens.
